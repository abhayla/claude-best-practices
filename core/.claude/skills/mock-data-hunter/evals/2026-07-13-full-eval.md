### Pattern analysis — confirmed defects

1. **CONFIRMED FUNCTIONAL BUG (STEP 1, highest severity):** the grep command `--include="*.{ts,tsx,js,jsx,py,vue,svelte,dart,kt,swift,rb,php,html}"` is written with the brace-expansion quoted, which prevents the shell from expanding it before grep receives the argument. GNU grep's `--include` does not itself interpret `{}` brace syntax. **Independently verified by direct execution** (see below) — the quoted form returns **zero matches / exit 1** against files that plainly match, while the unquoted (shell-expanded) form correctly matches:
   ```
   $ grep -rniE "mock|demo" --include="*.{ts,tsx}" src    → (no output), exit 1
   $ grep -rniE "mock|demo" --include=*.{ts,tsx} src       → src/a.ts:1:...  src/b.tsx:1:...  exit 0
   ```
   This is the worst possible failure mode for a skill whose entire premise is "don't trust a clean-looking sweep" — an agent following STEP 1 literally reports a **false CLEAN** on every real codebase.
2. **Scoping gap (STEP 1):** no guidance for chunking/prioritizing a large monorepo — `<src-dirs>` is an opaque placeholder with no runtime-budget or route-priority strategy.
3. **Structural placement risk (STEP 3):** the "run this substance-trace even when STEP 1 is clean" instruction lives ONLY in the bottom MUST DO section; STEP 3's own header text reads as scoped/conditional. Per `pattern-structure.md`'s own primacy+recency guidance (critical constraints at top AND bottom), this override should be inlined into STEP 3's procedural text, not left solely to the trailing MUST DO to carry it.
4. **Unoperationalized argument (frontmatter/STEP 5):** `--include-db` is declared but never explained in the STEP bodies.
5. **No idempotency/ordering convention (STEP 5):** repeat runs on an unchanged codebase have no stable ordering/ID guarantee, which could look like drift to a reviewer diffing two reports.

**Output verdict: FIX** (a confirmed functional bug in the skill's only executable command, plus a stress-test pass rate well under the ≥90% bar).
