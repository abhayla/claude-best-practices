## ROUND-1 DEFECTS — VERIFICATION OF FIXES

1. **CONFIRMED FUNCTIONAL BUG: quoted brace-expansion in STEP 1's grep `--include` silently
   zero-matched (false CLEAN)** — **CLOSED.** STEP 1's grep command now uses repeated
   `--include="*.ts" --include="*.tsx" --include="*.js" --include="*.jsx" --include="*.py"
   --include="*.vue" --include="*.svelte" --include="*.dart" --include="*.kt" --include="*.swift"
   --include="*.rb" --include="*.php" --include="*.html"` flags instead of the single quoted
   brace-list. This is the functionally correct form (each `--include` takes one literal glob, no
   shell/grep brace-expansion dependency) — re-verified by inspection against the same failure
   mode documented in round 1 (`--include="*.{ts,tsx}"` zero-matches; repeated flags do not have
   this failure mode since there is no brace syntax to mis-expand).

   ALSO ADDED (beyond the literal fix): a harness self-check — "Sanity-check the harness before
   trusting a clean result: plant `MOCKHUNT-CANARY` in a scratch file inside the sweep scope and
   confirm the command finds it, then remove it. A sweep that can't find the canary is broken,
   and its 'clean' means nothing." This is a stronger fix than the round-1 recommendation asked
   for — it doesn't just fix the one known bug, it adds a runtime self-test that would catch
   *any* future silent-zero-match failure mode (a different quoting mistake, a shell/grep version
   difference, etc.), not just the one diagnosed this round. This directly addresses the report's
   own warning that a broken sweep's "clean" means nothing.

2. **No monorepo scoping/chunking guidance** — **CLOSED.** STEP 1 now reads: "On large
   repos/monorepos, sweep per package/app directory (highest-traffic user-facing app first)
   rather than the whole tree at once; record which packages were swept vs skipped in the STEP 5
   scope line — an unswept package is not a clean package." STEP 5's locked output format's
   `Scope:` line was extended to `<dirs/URL swept, db included? y/n, packages skipped: [...]>`,
   giving the guidance a concrete place to land in the report.

3. **STEP 3's "run even when clean" override buried only in the bottom MUST DO section** —
   **CLOSED.** STEP 3's own opening sentence now reads: "run it EVEN WHEN STEP 1 came back clean
   (fabricated constants need no suspicious vocabulary; the recorded P0s rendered perfectly
   plausible numbers)." The override is now inlined at the point of use, not solely relying on
   the trailing MUST DO to carry it — satisfies the primacy+recency structural requirement this
   round-1 finding cited.

4. **`--include-db` argument unoperationalized in STEP bodies** — **CLOSED.** STEP 3 now reads:
   "With `--include-db`, extend the check into the live store itself: query for seeded-name
   patterns and future-dated rows among production records (the seeded-rows class), read-only."
   This explains both WHAT changes (direct live-store query, not just API/code trace) and the
   safety constraint (read-only).

5. **No idempotency/ordering convention for repeat runs** — **CLOSED.** STEP 5 now ends: "Order
   findings by file path so repeat runs diff stably; a re-run references issues already filed for
   unchanged findings instead of re-filing them." Provides both a stable ordering rule (file path)
   and a re-file-avoidance instruction.
