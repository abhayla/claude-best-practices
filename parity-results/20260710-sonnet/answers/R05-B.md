CASE-TAG: R05

**Answer:** The fix never became a new *version* — it's a content edit sitting inside the still-labeled-`0.3.1` source. Since the cache key is the version string (`cache/<plugin>/0.3.1/`), the updater's job is to compare the manifest version against what's already cached, not to diff file contents. Same version in → same version already present → updater sees "nothing to do" and serves the stale cached copy. The missing step is: **bump the manifest `version` (e.g. `0.3.1` → `0.3.2`) as part of the fix, and re-publish/re-tag so the registry/marketplace entry advertises the new version** — only then does the updater have a reason to pull a fresh copy into a new version-keyed directory.

**Reasoning:**
- Merging the source change alone only updates what's in the repo/registry blob; it does not touch the identifier the caching layer keys on.
- "Even after users run the updater" is the tell: if the updater ran and still shows the bug, it did its job correctly given its inputs — it checked version, found `0.3.1` already cached, and (correctly) did nothing. This is drift between "I merged a fix" and "I published a new release," not an updater malfunction — don't rationalize it as the updater being broken.
- Two things must both be true for users to receive it: (a) the manifest version bumped, and (b) the version bump actually pushed/merged (a local edit with an unbumped version, or a bumped version that never made it past CI, both reproduce exactly this symptom).
- Practically the fix is: edit source → bump `version` → merge → confirm the registry/marketplace metadata reflects the new version → then the update path resolves to a new `cache/<plugin>/0.3.2/` and serves the corrected code. Some plugin systems also require an explicit reinstall/update command rather than a passive "check on next launch" — worth confirming which model yours uses so users aren't waiting indefinitely for an auto-pull that never happens.

**Risk / what would change this answer:** If your updater instead keys on a content hash rather than the literal version string, the diagnosis would be different (a caching bug, not a missed version bump) — worth confirming which one your system actually does before treating "bump the version" as sufficient. Also confirm the merge actually shipped the bump (not just staged/reverted) — a version bump that didn't reach the branch users pull from reproduces the identical symptom.
