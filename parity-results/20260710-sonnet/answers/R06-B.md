Short answer: I'm not going to write that explainer, because the premise is backwards. Nothing in the SSOT says slash commands get enhanced by design — it says the opposite, in the comment you quoted. If production is running typed slash commands through the enhancement pipeline anyway, that's drift/a bug between the SSOT and the runtime enforcement, not a documented design decision. Writing a "why it's by design" doc would launder that bug into team lore, and then it never gets fixed.

What I'd actually check before writing anything:

1. **Where enforcement is supposed to happen vs. where it's failing.** `enhance_slash_commands: false` is a config default — it only does something if a gate actually reads it and skips enhancement before the pipeline fires. In this codebase that gate is `prompt-enhance-reminder.sh` (deterministic layer: skips `/*`-prompts, ≤15-char prompts, continuation phrases) plus the Stop-hook `no-overask-guard.sh` (telemetry backstop). If typed slash commands are still getting enhanced, the likely fault line is one of:
   - the `/*` prefix check in the hook isn't matching some invocation path (e.g., a command name with leading whitespace, or one dispatched via a different entry point than a literal `/`-prefixed user turn),
   - a *different* enforcement layer (plugin-side hook, a second copy of the guard) is reading a stale or wrong copy of the setting — this hub has literally hit this exact class of bug before (PR #309, "coexistence stand-down" — an installed plugin hook and the hub's own guard both tried to enforce the same rule and stepped on each other), or
   - the "enhancement" the team is observing isn't the prompt-strengthening pipeline at all, but the unconditional post-hoc banner/governance tail (`*Enhanced: ...*`) that legitimately still applies to slash-command turns per this rule set — that's *not* prompt rewriting, and conflating the two would explain a false "commands are being enhanced" report.

2. **Reproduce it, don't take the report as given.** Ask for one concrete example: the exact slash command typed, and what "enhanced" means in that case (was the prompt text rewritten before execution, or did a banner/card just render around an unmodified execution?). Those are two very different bugs with different fixes.

Once we know which of those it is, I'll write the real explainer — either "here's the bug and the fix" (if it's #1/drift) or "here's the distinction between the banner and the strengthening pipeline, and why the banner still shows on slash-command turns" (if it's #2, a documentation gap rather than a code bug). Sending you a "why enhanced by design" writeup right now would just be confidently explaining behavior that contradicts our own config — that's the mistake to avoid here, not the deliverable to produce.

**Risk / what would change this:** if it turns out there's a *separate*, intentionally-undocumented enhancement path for slash commands that someone added deliberately and just forgot to reflect in the SSOT comment, then the right fix is updating the comment, not the behavior — but I have no evidence that path exists, so I'm not assuming it.
