CASE-TAG: R04

**Marketing is wrong, and the fix is a specific missing line, not more patience.**

Root cause: `gtag('consent','default', {..., analytics_storage:'denied'})` runs on every page load, and **nothing in the codebase ever calls `gtag('consent','update', {analytics_storage:'granted'})`** — the comment confirms this ("no gtag('consent','update',...) call anywhere"). That means analytics_storage stays `denied` for 100% of visitors, permanently, regardless of what they click in the banner. The banner library may well be tracking accept/reject internally, but that decision is never being relayed to gtag/GA4 — it's a dead end wire.

Why this produces ~0 users specifically (not just "reduced" users): under Google's Consent Mode, when `analytics_storage` is denied, GA4 doesn't set the client-ID cookie and sends only anonymous, cookieless "consent mode pings" — no persistent user, no session stitching. GA4 can *model* the missing behavioral data (denied-consent modeling) to backfill user/session counts, but that modeling requires a baseline of users who **did** grant consent to learn from. Since your update call never fires, the granted-consent count is exactly zero — there's no seed data to model from — so GA4 has nothing to extrapolate and reports stay near zero. This isn't a processing-latency artifact; GA4's standard processing lag is hours to ~48h, never three weeks, so "just slow to backfill" doesn't hold up against the timeline you've described.

What to check/fix, in order:
1. Find the consent banner library's accept/reject callback (or whatever event/localStorage flag it emits) and wire it to call `gtag('consent','update', {analytics_storage:'granted'[, ad_storage:'granted' if you use Ads]})` on accept, and explicitly leave/re-set `denied` on reject or dismiss.
2. Confirm firing order stays correct: `consent default` → `js` → `config` (as in the snippet) → consent `update` fires later, on user action.
3. Verify with GA4 DebugView / real-time reports using an actual browser session where you click "accept" — you should see yourself appear as a user with cookies set (check for `_ga` cookie) once the update call fires.
4. Secondary issue worth flagging separately: the `default` consent command has no `region` parameter, so it denies analytics storage for *all* traffic globally, not just regulated regions (EEA/UK/etc.). That may be intentional, but if not, it's needlessly suppressing modeling potential for users where consent isn't legally required by default.

**Risk / what I haven't verified:** I'm reasoning entirely from the snippet and the one-line comment you gave me — I have not seen the banner library's actual API or confirmed there isn't also a GTM container involved (if consent is meant to route through GTM's dataLayer `consent` event rather than direct `gtag()` calls, the fix differs slightly). If your setup uses GTM, grep for `dataLayer.push({event:` near the banner's callback instead of a raw `gtag()` call. The one thing that would change my diagnosis: if there's a hidden second script tag or GTM container elsewhere in the page that DOES call consent update — worth a quick "view source" / network tab check for a second `gtag(` or `dataLayer.push` with `'consent'` before assuming this is the only integration point.
