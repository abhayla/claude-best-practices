**The spec as written is self-contradictory, and I'm not going to draft around it silently.**

(a) says worst-case latency ≤ 5s. (b) says the only detection mechanism is a poll that fires once every 60s. Those two can't both hold: if an alert lands in the queue 1 second after a poll completes, it sits there for up to 59 seconds before anyone even looks — no code on the delivery side can shrink that, because the alert hasn't been *seen* yet. This isn't a tuning problem, it's arithmetic: max latency from a fixed-interval poll is bounded below by the poll interval, not by anything downstream. Shipping a design that quietly assumes 60s→"eventually" and calling it "5s delivery" would be handing you a spec that fails its own acceptance test on day one.

So there are exactly two ways to close this gap, and (c) rules out the one everyone reaches for first (push/streaming). Here's the approach, built around the one that's actually available:

**Recommended: pull-based long-polling, not fixed-interval short-polling**

"Poll the queue" doesn't have to mean "wake up on a 60s timer, check, sleep." Every mainstream queue (SQS `ReceiveMessage` with `WaitTimeSeconds`, GCP Pub/Sub pull subscriptions, RabbitMQ basic.consume with prefetch, Redis `BLPOP`) supports a **blocking pull**: the worker issues a receive call that the broker holds open and returns from the *instant* a message arrives (or after a timeout if the queue's empty). This is still 100% pull — no broker-initiated push, no SSE/WebSocket layer, nothing that fails the "no streaming infra" constraint — but latency is bounded by network/processing time (low hundreds of ms), not by a fixed interval. It's also *cheaper* than a 60s fixed poll under load, because you're not burning a request every minute against an empty queue; you hold one connection open and pay per message, not per tick.

Concretely:
- N worker processes each hold a long-poll connection (e.g., SQS `WaitTimeSeconds=20`, auto-reconnect on timeout/empty return).
- On message receipt: validate → route to the appropriate channel adapter (email/SMS/webhook/etc.) → send → ack/delete from queue only after confirmed send (at-least-once, not at-most-once — a crash between receive and send just means visibility-timeout requeue and a possible duplicate, which the alerting UI should already dedupe on alert ID).
- Failed sends go to a retry queue with backoff; a dead-letter queue catches anything that exhausts retries, alerting *on the alerting system* separately.
- Concurrency (worker count × in-flight capacity) is sized to keep processing-side latency (message received → send attempted) in the low hundreds of ms so the 5s budget is spent almost entirely on transport, not queueing.
- Cost stays controlled because you scale workers to queue depth, not to a fixed cadence — idle periods cost one held connection per worker, not per-minute API calls.

**If "polls once per minute" is a hard, literal constraint** (e.g., a platform limitation that genuinely disallows a blocking receive, not just a cost-saving preference), then (a) is not achievable as stated — worst-case latency is bounded below by ~60s, full stop. In that case I'd rather tell you now than ship a design with a silently-broken SLA: either the 5s target needs to be relaxed (e.g., "5s from poll-detection" instead of "5s from event"), or the polling constraint needs to allow blocking receive semantics as above.
