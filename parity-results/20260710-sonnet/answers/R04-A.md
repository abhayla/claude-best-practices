CASE-TAG: R04

This is not a GA4 backfill delay — it's a self-inflicted consent-mode deadlock, and it will never resolve on its own no matter how long marketing waits.

**Root cause**

The snippet sets:

```js
gtag('consent', 'default', {
  ad_storage: 'denied',
  analytics_storage: 'denied'
});
```

That `default` command tells gtag.js: "until told otherwise, treat every visitor as opted out of analytics." Consent mode then suppresses (or, without Consent Mode v2 basic/advanced settings, heavily limits) hit collection — it doesn't queue data for later, it drops it. GA4 is reporting ~0 users because it is genuinely receiving ~0 (or unmodeled, filtered-out) analytics hits, not because of ingestion lag. GA4's real processing latency is hours, not weeks — "just slow to backfill" doesn't hold at three weeks.

The comment in the snippet is the smoking gun: *"no `gtag('consent','update',...)` call anywhere in the codebase."* Whoever wired in the consent banner added the default-deny state (correct, required for GDPR/CCPA compliance-by-default) but never wired the banner's "accept" action back into gtag. So:

- Users who accept cookies → still stuck at `analytics_storage: 'denied'` forever, because nothing ever calls `update`.
- Users who reject → correctly denied (this part is fine).
- Net effect: 100% of sessions run under the denied default, regardless of what the user actually chose in the banner.

That's why server logs (which don't care about JS consent state) show thousands of daily requests while GA4 shows ~0 — the traffic is real, the client-side analytics beacon is being suppressed for everyone.

**Fix**

1. In the consent banner's accept/save handler, add:
   ```js
   gtag('consent', 'update', {
     ad_storage: 'granted',   // or leave denied if only analytics consent is asked
     analytics_storage: 'granted'
   });
   ```
   This must fire immediately when the user accepts, and also on page load if a prior consent choice is already stored (e.g., in a cookie/localStorage the banner lib manages) — otherwise returning visitors who accepted on visit 1 still get denied on visit 2 until they click again.

2. Confirm the banner library actually exposes a callback/event for "user accepted" / "user changed preferences" — wire `gtag('consent','update', …)` into that hook, not into a `DOMContentLoaded` fire-and-forget.

3. If you want partial signal even from undecided/rejected users, consider enabling **Consent Mode v2 behavioral modeling** (`ad_user_data`/`ad_personalization` fields, plus GA4's built-in modeling for denied consent) — but that's an enhancement, not the bug fix. Don't let that distract from item 1.

4. Verify with DebugView or the browser network tab: after clicking "Accept," you should see a `collect` request with `gcs` reflecting granted state (e.g., `gcs=G111` vs `G100`), and DebugView should start showing events in real time — not next week.

**What to tell marketing**

Don't wait — there is nothing to backfill. GA4 doesn't retroactively recover data it never collected. Every day this ships unfixed is permanently lost measurement, not a delayed-but-recoverable dataset. Push for the one-line `consent update` fix today; you should see users reappear in GA4 Realtime within minutes of deploying it, which will also serve as your verification.
