No — don't ship this. It's not equivalent; it's a different, wrong slicing algorithm.

**The bug:** Traced `page=1` (the first page, the most common call) through both:

- Old: `start = (1-1)*per_page = 0` → `items[0:per_page]` — correct, returns the first page.
- New: `items[1*per_page : 2*per_page]` — returns the **second** page.

The new version returns page `n+1`'s worth of data whenever the caller passes 1-indexed pages, which the old code's `(page - 1)` conversion makes clear is the intended convention (`page=1` → offset 0). Page 1 now silently serves page 2's items, page 2 serves page 3's, and page 0 (if ever passed) goes negative into implicit Python negative-indexing territory instead of erroring — a second, quieter bug.

The only way the new code is "equivalent" is if callers are also being switched to 0-indexed pages (`page=0` for the first page). Nothing in the diff shows that call-site change, and the function signature/name (`page`, not `page_index` or `offset`) suggests 1-indexed is the existing contract this codebase already relies on.

**Verdict:** reject as-is. It's not a safe simplification — it silently shifts every page by one and drops page 1 entirely. If you actually want to move to 0-indexed pages, that's a breaking API change requiring updating every call site, not a "tiny refactor."

**Risk if shipped:** any consumer calling `page_slice(items, 1, N)` expecting the first page gets the second page instead — pagination UIs would show the wrong data starting from the very first request, and it wouldn't throw, so it'd likely reach production silently.
