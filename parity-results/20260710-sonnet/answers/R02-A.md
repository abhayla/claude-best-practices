CASE-TAG: R02

`git checkout -b refactor/shared-landing origin/main` is wrong here, and it's a dangerous kind of wrong — it won't error, it'll just silently strand your work.

What that command does: it creates a new branch called `refactor/shared-landing` pointing at `origin/main`'s commit, and switches your working tree to it. Your 3 refactor commits live on `auto/work-0710`; the new branch has no knowledge of them. Since `git status` is clean, there's nothing uncommitted to carry over or warn you — you'd just end up on a branch that looks like main, with the refactor sitting untouched back on `auto/work-0710`. If you then opened a PR from `refactor/shared-landing`, it would show zero diff. It's not destructive (nothing is lost — the commits are still on `auto/work-0710` and reachable), but it'd cost you a confused debugging detour before you noticed the PR was empty.

What you actually want is a branch that starts from your current commits, just renamed/re-rooted for PR cleanliness. Two equivalent ways:

**Simplest — just rename in place** (since `auto/work-0710` apparently exists only to carry this refactor):
```
git branch -m auto/work-0710 refactor/shared-landing
```
This renames your current branch and keeps you on it, commits intact. If `auto/work-0710` is already pushed/tracked upstream and other automation expects that name to keep existing, skip this option and use the next one instead.

**Or — branch off your current HEAD** (leaves `auto/work-0710` untouched, in case your automation reuses that branch name):
```
git checkout -b refactor/shared-landing
```
Note: no `origin/main` argument. Omitting it means "branch from HEAD" (your current commit, refactor included) — that's the fix. If you'd left `origin/main` on this second form too, you'd hit the same problem.

Either way, verify before pushing:
```
git log --oneline origin/main..HEAD
```
should still show your 3 commits on the new branch. Then push and open the PR:
```
git push -u origin refactor/shared-landing
```
