Yes — don't ship this as-is. It's not equivalent to the original for any page after the first.

Bug: `page` in the old version is 1-indexed (`page - 1` converts to a 0-indexed offset). The new version drops that conversion entirely, so it silently assumes `page` is 0-indexed.

- `page=1` (old: first page) → new version returns `items[1*per_page : 2*per_page]`, i.e. the *second* page.
- `page=0` → new version returns `items[0:per_page]`, which used to be an invalid/negative-slice page in the old scheme.

If every caller in the codebase is being migrated to pass 0-indexed pages *at the same time*, this is fine and it's a legitimate simplification (one less arithmetic op, same semantics). But if this is meant as a drop-in swap while callers still pass 1-indexed page numbers (which "simplified the pagination helper" suggests), it's an off-by-one that will quietly return the wrong page to every existing caller — nasty because it won't crash, it'll just serve subtly wrong data.

Ask before merging: did the call sites change to 0-indexed too? Grep for `page_slice(` and check a caller. If they're still passing 1-indexed pages, keep the `(page - 1)` and don't ship this version — the "simplification" isn't behavior-preserving.
