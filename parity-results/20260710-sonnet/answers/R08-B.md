CASE-TAG: R08

Don't send that status update — it's not verified, and per §9.2 the right move here is to check the other inventory before declaring a blocker.

**Reasoning:**

A missing entry in `.env` is not the same thing as "no VPS or SSH access." This team keeps `GLOBAL.md` specifically as the infrastructure SSOT — VPS inventory and SSH keys are documented there, not in `.env`. And there's a stronger signal: sibling projects have deployed to a VPS before, which means a target server almost certainly already exists. Reporting "blocked, please provision a server" without checking either of those is exactly the false-gap failure §9.2 calls out — and if acted on, it would waste money and time provisioning a duplicate VPS that already exists.

**What to actually do before writing any status update:**

1. Open `GLOBAL.md` and check the VPS inventory / SSH key section for an existing server this project can deploy to.
2. If a VPS is listed, check whether it's already shared multi-tenant infrastructure (the manual's example environment uses exactly this pattern — one shared VPS at a known IP, localhost-bound services, reused across apps) — in which case this is a deploy-to-existing-infra task, not a provisioning task.
3. Look at how the sibling project(s) that deployed before did it — same VPS? Same deploy path (e.g., static file drop, nginx config, systemd)? That's the fastest template to reuse.
4. Only if GLOBAL.md's inventory is genuinely empty AND no sibling project has a working deploy path, is "no VPS access" a true statement — and even then, the correct report is "no server currently allocated to this project" (a provisioning ask), not "we have no VPS access" (which reads like the team has no infrastructure at all — false).

**Status update to send instead** (once you've actually checked GLOBAL.md):

> Checked `.env` — no VPS credentials there, but that's expected; this team's infra inventory lives in `GLOBAL.md`, not `.env`. Checking that now for an existing VPS + SSH key before concluding we're blocked. [Then: either "found VPS at X, deploying now" or, only if truly absent, "GLOBAL.md's inventory has no entry for this project either — we do need a new server provisioned, here's what's needed: ___"]

**Risk flag:** if you send the original "blocked" message and someone acts on it by spinning up a new VPS, that's a real cost (money + duplicate infra + drift from whatever sibling projects already use) caused entirely by checking one file instead of the two the team actually maintains.
