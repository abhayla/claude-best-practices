That's a version-cache-key mismatch, not a bug in your fix — the fix is correct, it just never reaches anyone because you skipped the one step that actually invalidates the cache.

**Why it's not reaching anyone:** the plugin host caches installed plugins under `cache/<plugin>/<version>/` and always serves from that directory. That means "what's installed" is keyed on the version *string* in the manifest, not on file contents, not on the commit hash, not on "did the source change." Your updater's job is to compare the manifest's declared version against what's cached and pull a new copy only if the version differs. You edited source and merged, but the manifest still says `0.3.1` — identical to what every user already has cached. So the updater does exactly what it's supposed to do: sees `0.3.1 == 0.3.1`, concludes there's nothing new, and serves the stale cached copy. Users aren't failing to update — there's nothing for the updater to detect as an update.

**The missing step:** bump the manifest's `version` field (e.g. `0.3.1` → `0.3.2`) as part of the fix, before/at merge — not after. This is load-bearing, not cosmetic: it's the cache key. An un-bumped source edit is invisible to every consumer of the version-keyed cache; there's no other invalidation path (no content hash, no mtime check implied by the design as you've described it).

**What to do now:**
1. Bump the version in the manifest (patch bump is enough for a bug fix — `0.3.2`).
2. Merge that as its own commit/PR if the fix is already merged.
3. Re-run/verify the updater against a fresh cache dir to confirm it pulls `cache/<plugin>/0.3.2/` and that the fix is actually present there (don't just trust the version number changed — read the file back from cache).
4. If your tooling allows it, add a CI check that fails a merge which touches plugin source without touching the version field — this exact class of "fixed but shipped nothing" bug will recur otherwise, since it's an easy step to forget under normal review pressure.

One thing to double check on your end: whether your users' "run the updater" actually re-resolves the manifest from your repo (git) or from some published registry/index that itself needs republishing after the version bump. If there's a registry/index in between, bumping the manifest version in your repo alone won't be enough — the index also needs to pick up the new version before any updater will see it.
