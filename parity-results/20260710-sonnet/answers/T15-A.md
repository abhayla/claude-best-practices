Your teammate is wrong about what's deployed. `retries.enabled: true` with `max_attempts: 4` — but the log shows `attempt 1 of 1`. That's not "retries disabled to avoid duplicate side-effects," that's the retry logic not running at all despite config saying it should.

A few concrete possibilities, in order of likelihood:

1. **Config not actually loaded / stale reload** — the running process may be reading a cached or previous version of `webhooks.yml` (no restart/reload after the last config change). "Attempt 1 of 1" reads exactly like the *hardcoded default* before this retry feature existed, or like a fallback path that never got wired to `retries.max_attempts`.
2. **Wrong config scope** — there could be a per-endpoint or per-webhook-type override (e.g., `order-created` specifically) that disables retries independent of the global `delivery.retries` block. Worth checking if there's an endpoint-level config that shadows this.
3. **Retry gate on status code** — some retry implementations only retry on specific conditions (timeouts, 5xx from a specific list, idempotency-key present, etc.) and silently skip retry eligibility checks for 503 if that code isn't in the retryable set — but then the log message would normally say "not retryable" rather than "giving up," so this is less likely given the log text.
4. **A separate kill-switch was flipped** — e.g. an env var or feature flag (`WEBHOOK_RETRIES_DISABLED=1`) overriding the YAML at runtime, which is a common pattern and would fully explain both this line and your teammate's mental model (they may be remembering a flag they set, not this file).

**What I'd actually check before writing this off as intentional:** grep the delivery service's startup logs for the parsed config values it thinks it's running with, and check for any env var / feature flag that overrides `delivery.retries.enabled`. If the service logs "retries: enabled=true, max_attempts=4" at startup but still gives up after 1 attempt, that's a code bug in the retry-eligibility check, not a config issue — likely someone added a duplicate-suppression guard downstream of the retry decision that unconditionally short-circuits after attempt 1, which is probably the actual mechanism your teammate is remembering as "we disabled retries."

**To the team:** this isn't a policy decision currently in effect — the deployed config explicitly asks for 4 attempts with exponential backoff, and we're getting 1. Before we decide whether retries *should* be on (a real conversation given the duplicate-side-effect concern, and one worth having explicitly — e.g. via idempotency keys instead of no-retries), we need to find why the config value isn't reaching the delivery path. I'd bet on stale config load or an undocumented kill-switch, not the YAML being wrong.
