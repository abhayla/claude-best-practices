Don't ship as-is — this isn't a simplification, it's a semantics change from 1-based to 0-based pages.

The two versions differ by exactly one page for every input:

- **Old:** `page=1` → `items[0:per_page]` (first page)
- **New:** `page=1` → `items[per_page:2*per_page]` (second page)

So if your callers pass 1-based page numbers (which the old code clearly expects — the UI convention of "page 1" being the first page), the new version silently skips the first page and shifts everything off by one. Worst part: it fails quietly — no exception, just wrong data, and on the last page you'd get an empty list where there used to be results. That kind of off-by-one in pagination tends to survive code review and get caught by a customer.

Your options:

1. **Keep the old version.** `(page - 1) * per_page` is idiomatic for 1-based pagination; there's nothing wrong with it and the "simplification" saves nothing real.
2. **If you genuinely want 0-based pages**, ship the new version *plus* an audit and update of every caller (API param parsing, defaults like `page=1` in route handlers, frontend links, docs). That's a migration, not a tiny refactor.

One extra note either way: neither version validates `page`. With the old code, `page=0` gives `start=-per_page`, and Python's negative slicing will silently return a *wrong* slice (tail of the list) rather than erroring. If you touch this function anyway, adding a `page < 1` (or `< 0` for 0-based) guard is worth the two lines.

Also: if there's a test suite covering this helper and it passed with the new version, that's a red flag about the tests, not reassurance — a correct test of "page 1 returns the first `per_page` items" must fail against the new code.

**Recommendation:** revert to the old version unless a deliberate 0-based migration is actually the goal.
