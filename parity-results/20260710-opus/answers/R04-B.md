## Diagnosis: GA4 is broken, not backfilling. Do not wait.

The banner isn't slow — it's severing analytics. Your snippet sets `analytics_storage: 'denied'` as the default and **there is no `gtag('consent','update',...)` call anywhere**, which you already noted. That means consent is denied for every visitor, forever, including the ones who click "Accept." The consent banner is loaded but never wired to gtag, so accepting does nothing. GA4 can't set its `_ga` cookie, can't identify or count users, and reports ~0. This started the day you added the banner — that timing is the diagnosis, not a coincidence.

Marketing's "slow to backfill" theory is wrong on the facts: GA4 Realtime populates within seconds and standard reports within ~24–48h. It does not sit at zero for three weeks and then catch up. Three weeks of zero is a dead pipeline. Another week gets you a fourth week of zero.

**Why the numbers look the way they do:** your server logs count all HTTP requests (bots, assets, retries), so "thousands of requests" overstates humans — but that gap doesn't explain ~0. Real users exist; GA4 just can't record an identifiable session because consent is never granted.

## Root cause

The accept action on the cookie banner is not connected to a consent update. Consent Mode is doing exactly what you told it: default deny, never upgrade.

## Fix

1. **Wire the banner's "Accept" handler to fire the update** — the single missing line:
   ```js
   gtag('consent', 'update', {
     ad_storage: 'granted',
     analytics_storage: 'granted'
   });
   ```
   Fire it on accept (and only for the categories the user actually accepted). On the next page load the default-denied state applies again until the stored consent choice re-grants it, so the banner lib must also replay the saved choice into a `gtag('consent','update',...)` on every load — check that it does.

2. **While you're in there, verify two things** (flagging, not assuming):
   - `gtag.js` for your real measurement ID is actually loaded — the snippet calls `gtag()` but the loader isn't shown, and `G-XXXX` is a placeholder. Confirm the real `G-` ID is in the live page, not the redaction.
   - The banner writes a persisted consent choice that survives navigation, or every page reverts to denied.

3. **Verify the fix by observation, not by assertion:** open the site, accept the banner, and in DevTools → Network confirm a request to `/g/collect` fires with the consent params and the `_ga` cookie gets set. Then watch GA4 **Realtime** — users should appear within a minute or two. That's the gate; "the code looks right" is not.

## Risks / what would change this

- **If you see ~0 in Realtime even after wiring the update:** the problem is upstream of consent (wrong/absent measurement ID, gtag.js not loading, an ad-blocker test environment). Same 15-minute check, different culprit — still not backfill.
- **One honest nuance:** in *advanced* consent mode GA4 sends cookieless "denied" pings that produce some modeled data, so a strict setup usually shows a small non-zero, not a clean zero. A true ~0 means the tag effectively isn't collecting at all (behaving like basic mode / blocked) — which only strengthens the conclusion that the pipeline is broken, not lagging.
- **Privacy note:** whatever the fix, users who decline must stay unmeasured by design. The bug is that users who *accept* are also unmeasured. That's the part to restore.

Net: this is a code fix measured in minutes and verifiable today. Don't spend the week waiting on a backfill that isn't coming.
