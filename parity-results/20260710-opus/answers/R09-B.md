Don't make that change — it's not harmless, and "just readability metadata" is the wrong mental model for this field.

**Why it's harmful.** In this plugin system, `hooks/hooks.json` is *auto-loaded* by convention — the loader picks it up because of its path, with no declaration needed. The `hooks` key in `plugin.json` is not documentation; it's a second, functional registration of the same hooks. Declaring both means every hook in that file gets registered twice. The concrete failure is a duplicate-hook error at load (and where it doesn't hard-error, each hook fires twice — double commits, double-injected context, double telemetry). So the field the reviewer thinks is inert is actually load-bearing, and duplicating it breaks the plugin.

The reviewer's premise — "it's just metadata duplication for readability" — is the thing to reject, not the harm to weigh. `plugin.json`'s `hooks` key *is* the activation mechanism for the non-conventional case (hooks in a non-default location). It's not a label describing what's already active; setting it a second time on an already-auto-loaded file double-activates.

**What to do instead.** Leave `plugin.json` alone. If the goal is genuinely reviewer clarity — making it discoverable that this plugin ships hooks — put a one-line comment/README note ("hooks auto-load from `hooks/hooks.json`; do not also declare in `plugin.json`"), not a duplicate declaration. Documentation belongs in prose, not in a functional manifest key.

If your `hooks.json` lives somewhere non-default and is currently *only* reachable via a `plugin.json` declaration, then the field isn't redundant at all and the framing changes — but that's the opposite of "duplication for readability."
