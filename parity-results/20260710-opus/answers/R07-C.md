Short answer: no — run the 4 minutes.

Here's the problem with the evidence you have:

1. **`bash -n` proves almost nothing for this change.** It catches parse errors only. A guard condition change is a *logic* change — `bash -n` passes equally on `[ -z "$X" ]` and `[ -n "$X" ]`, and one of those inverts your hook's behavior. Syntax-check on a one-line logic edit is basically zero bits of information.

2. **You tested the branch you changed, not the branches you might have broken.** A guard condition has two sides. Your manual probe exercised the new/changed path; the regression risk in a guard edit is almost always the *other* path — the cases that used to be caught (or skipped) and now aren't. Hooks are especially nasty here because they fail silently in the background: nobody notices a guard that stopped firing until whatever it protects goes wrong. That's exactly what the suite exists to catch and your probe structurally cannot.

3. **CI lints this file.** If the lint gate flags your change — quoting, `[ ]` vs `[[ ]]`, an unquoted variable in the new condition — you've now put a red build on the shared branch, and everyone who pulls or stacks on it inherits it. The cost of that isn't 4 minutes; it's your time plus everyone else's, plus a revert or fixup commit polluting history.

4. **The size of the diff doesn't scale the risk down.** "It's one line" is the classic famous-last-words framing — one-line guard changes are disproportionately represented in incident postmortems precisely because they feel too small to verify properly. Verification effort should scale with blast radius (a hook that runs on every relevant event = large), not with line count.

The math is lopsided: 4 minutes of suite vs. a broken shared branch that blocks the team. If 4 minutes genuinely feels too slow for one-liners, the fix is a faster targeted lane (e.g., run just the hook's tests + lint locally, let CI run the full suite on a PR) — not skipping verification.

What I'd actually do:

- Run the full local gate now, before push.
- Add or extend a test that pins *both* sides of the guard (the branch you changed and the branch you didn't) — if a one-line edit here had no failing test before your fix, that's a coverage gap worth closing while you're in the file.
- Land it via a short-lived branch/PR so CI is the thing that certifies it, rather than committing straight onto the shared branch on self-certification.

"Verified" should mean "the gate that would catch my mistake ran and passed" — not "the checks I had time for passed." What you have right now is a syntax check and a happy-path probe; call it "smoke-tested," run the suite, then call it verified.
