Diagnosis: this is not a backfill delay. It's a Consent Mode misconfiguration, and the data you didn't collect over the last three weeks is gone permanently. Do not wait a week.

## Root cause

Your snippet sets the Consent Mode default to denied:

```js
gtag('consent', 'default', { ad_storage: 'denied', analytics_storage: 'denied' });
```

`analytics_storage: 'denied'` tells GA4 it may **not** write the `_ga` cookie or read/persist a `client_id`. That's the correct, privacy-safe default to ship *before* the banner resolves.

The bug is the part your own comment already flags: **there is no `gtag('consent', 'update', ...)` call anywhere.** When a visitor clicks "Accept" on the banner, nothing ever flips `analytics_storage` from `denied` to `granted`. So every visitor, consented or not, stays in the denied state for their entire session, forever.

Consequence chain:
- No `client_id` cookie is ever set → GA4 has no stable identifier to attribute hits to.
- User/session counts in GA4 are built on `client_id`. No identifier → **~0 users**, exactly what you're seeing.
- The timing is the giveaway: it broke the day the banner shipped. That's causation, not coincidence. GA4 was fine before because there was no consent gate suppressing storage.

What you *might* still see is a trickle of "modeled" or cookieless-ping data, but for most properties that renders as near-zero in standard user reports and requires behavioral-modeling thresholds you almost certainly aren't hitting. That's not your traffic showing up — it's an artifact.

## Why "wait for backfill" is wrong

GA4 is near-real-time (minutes, not weeks) and **does not backfill**. It can only report on hits it actually received and was permitted to store. For three weeks it was told "storage denied" on every hit, so there is nothing queued to arrive. Waiting another week doesn't recover the missing three — it just adds a fourth week of zero. Every day this stays broken is another day of permanently lost analytics.

## The fix

Wire the banner's accept action to an `update` call:

```js
// on "Accept" (analytics category granted):
gtag('consent', 'update', { analytics_storage: 'granted' });
// (and ad_storage: 'granted' only if they accepted the marketing/ads category)
```

Most consent libraries (CookieYes, Cookiebot, Osano, Iubenda, a homegrown banner) expose an on-accept callback or emit an event — hook the `update` into that. Also make sure it fires for **returning** visitors who already consented on a prior visit (replay stored consent on page load), not just first-time acceptors.

Two things to verify while you're in there:
1. Confirm `gtag.js` (`googletagmanager.com/gtag/js?id=G-XXXX`) is actually loaded and the `gtag`/`dataLayer` stub is defined before these calls — the snippet doesn't show the loader, and if the banner lib reordered script execution, `gtag` could be undefined and throwing.
2. Confirm the banner isn't *also* blocking the GA script from loading at all (some CMPs do consent-gated script injection). If so, the script needs to load in Consent Mode from the start, not be withheld.

## How to confirm in ~10 minutes (before touching prod)

- Open the site, DevTools → Network, filter `collect` (or `g/collect`). You'll see the GA hit go out with `gcs=G100` (analytics denied). Click Accept. **Currently** the parameter won't change → proof consent never updates. After the fix, accepting should flip it to `gcs=G111`.
- Or use GA4 DebugView / the Google Tag Assistant and watch the consent state change on Accept.

Tell marketing: the number isn't slow, the pipe is closed. Ship the `update` call today, verify with the `gcs` flag, and you'll see users return to normal within minutes — but the three-week hole stays a hole.
