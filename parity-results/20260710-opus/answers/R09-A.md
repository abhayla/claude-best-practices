Short answer: don't do it. This isn't harmless metadata duplication — it's a functional double-registration, and it will bite us.

Here's the mechanism. The plugin system already auto-loads `hooks/hooks.json` by convention. That file *is* the hook source of truth; the loader picks it up on its own. Adding `"hooks": "./hooks/hooks.json"` to `plugin.json` points the manifest at the very same file, so the loader ends up registering those hooks a second time. Two failure modes, depending on the loader version:

- It errors out on the duplicate declaration (plugin fails to load — worst case, silently, so the whole plugin goes dark).
- It "succeeds" and every hook fires twice per event. For anything non-idempotent — a Stop-hook that writes a log line, a formatter that rewrites a file, a notifier that pings someone — double-firing is a real bug that's annoying to trace back, because on paper the config "looks clean."

So the reviewer's premise is the flaw: `plugin.json`'s `hooks` key and the auto-loaded `hooks/hooks.json` are not "the manifest describing the file" — they're two independent registration paths for the same hooks. Declaring both means registering twice, not documenting once.

The general rule we should keep: **never declare hooks in `plugin.json` — they auto-load from `hooks/hooks.json`, and double-declaring is an error, not documentation.** (Same caveat doesn't apply to skills/commands, which is probably where the reviewer's "for clarity" instinct comes from — but hooks specifically are auto-discovered.)

If the actual goal is discoverability — making it obvious to a future reader that this plugin ships hooks — the safe way to get that is a one-line note in the plugin README pointing at `hooks/hooks.json`, not a second live registration in the manifest.
