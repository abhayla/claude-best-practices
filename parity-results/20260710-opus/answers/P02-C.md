Before drafting anything: this spec can't be built as written — two of the three constraints are mathematically incompatible, and I'd rather flag that now than hand you an approach that fails its own SLA on day one.

## The conflict

- **(a)** says every alert delivers within **5 seconds**.
- **(b)** says we poll the queue **once per minute**.

With a 60-second poll interval, an alert enqueued right after a poll waits up to ~60s just to be *picked up*, before any processing or delivery time. Average pickup latency is ~30s; worst case ~60s+. Constraint (a) is violated for roughly **92% of alerts** (anything arriving more than 5s before the next poll). No implementation cleverness fixes this — it's arithmetic, not engineering.

**(c)** (no new push/streaming infra this quarter) rules out the obvious escape hatch (webhooks, SSE, message-broker consumers with push semantics), but note: it does *not* necessarily rule out the fixes below, depending on what queue we already have.

## Options — pick one, and the spec owner must choose

**Option 1 — Tighten the poll interval (recommended if (a) is the hard requirement).**
Poll every 1–2 seconds instead of every 60. This stays 100% within (c) — it's still polling, no new infrastructure. Cost impact is usually the stated fear, but it's often negligible in practice:
- If the queue is SQS: use **long polling** (`WaitTimeSeconds=20`). One in-flight receive call held open by the server gives near-instant delivery (typically <100ms pickup) at ~3 requests/minute/worker — *cheaper* than many short polls and well within (a) and (c). This is the sweet spot: it's still a poll-based API call, not push infrastructure.
- If it's a database-backed queue: `SELECT ... FOR UPDATE SKIP LOCKED` every 1–2s is a trivial indexed query; cost is effectively zero at alert-service scale.

**Option 2 — Relax (a) to match (b).**
If once-per-minute polling is truly the cost ceiling, the honest SLA is "delivered within ~90 seconds" (60s max pickup + processing + provider latency). If the business can live with that, say so in the spec and I'll build to it.

**Option 3 — Tiered.**
Critical alerts on a 1–2s (or long-poll) path, everything else on the 60s batch poll. Only worth the complexity if there's a real cost driver behind (b), which I doubt.

## Proposed technical approach (assuming Option 1, which I recommend)

**Assumption:** the queue is SQS or similar (has long-poll support) or a DB table. If it's something else, tell me and I'll adjust — the shape below still holds.

1. **Consumer:** a small worker loop doing long-poll receive (20s wait) or a 1s-interval indexed DB poll. Single worker to start; horizontal scale later only if throughput demands it (YAGNI).
2. **Delivery:** on dequeue, dispatch to the channel provider (email/SMS/webhook-out — outbound calls are fine under (c); the constraint is about *inbound* push infra). Budget: pickup <1s, dispatch <2s, leaving ~2s headroom on the 5s SLA.
3. **Reliability:** visibility timeout / row lease + at-least-once semantics; idempotency key on the alert ID so retries never double-send. Dead-letter after N failures with an ops alert.
4. **SLA measurement:** stamp `enqueued_at` on every message; emit `delivered_at - enqueued_at` as a metric with an alarm at p99 > 5s. Without this, (a) is unverifiable — the SLA must be observed, not assumed.
5. **Failure mode:** if the delivery provider is slow/down, the 5s SLA is breached regardless of our pickup speed — the SLA should be scoped as "within 5s *of our service handing off to the provider*" or the provider's latency must be part of the budget. Flag for the spec owner.

## What I need before building

One decision from whoever owns the spec: **is (a) or (b) the real constraint?** They cannot both stand. My recommendation is keep (a), replace (b) with "long-poll / short-interval polling (no push infra)" — it satisfies the *intent* of (b) (cost control) and the letter of (c), and (a) becomes achievable. If that's approved, the approach above is ready to implement.
