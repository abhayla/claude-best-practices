The fix isn't reaching anyone because **you never bumped the version, and the cache is keyed by version** — the updater has no other change signal.

**The failure chain:**

1. The plugin system copies an installed plugin into `cache/<plugin>/<version>/` at install time and serves every session from that snapshot — never from your repo.
2. When a user runs the updater, it compares the manifest `version` of the latest published source against what's cached. Your manifest still says `0.3.1`; the cache already has a `cache/<plugin>/0.3.1/` directory, so the updater concludes "already current" and does nothing. It does not diff file contents or hashes — the version string *is* the cache key and the freshness check.
3. Result: your fixed source sits in the repo under the same version label as the buggy snapshot, and by design the buggy snapshot wins forever. An un-bumped source edit is unreachable by every existing install.

**The missing step:** bump the manifest `version` (e.g., `0.3.1` → `0.3.2`) as part of the fix, then land it. On the next update, the updater sees `0.3.2 > 0.3.1`, fetches into a new `cache/<plugin>/0.3.2/` directory, and serves the fixed code. Users who already "updated" today will need to run the updater once more after the bump lands (or reinstall).

**Verify it actually propagated** — don't trust "updater ran": check that `cache/<plugin>/0.3.2/` now exists on an installed machine and that the fixed file inside it contains your change. That's the ground truth.

**Process fix so this doesn't recur:** make the version bump a mandatory step of every plugin fix — the sequence is *test locally → bump version → land → verify the installed copy*. This exact trap is why our hub routes all plugin maintenance through `/plugin-lifecycle`, which hard-codes the bump as load-bearing (see `docs/installing-plugins-in-downstream-projects.md` and the `reference_cc_plugin_install_cache` note: source edits need a version bump + update/reinstall to reach anyone). If your release tooling allows it, add a CI check that rejects a PR touching plugin source without a corresponding `version` change — that turns a silent no-op release into a red build.
