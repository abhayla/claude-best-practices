I wouldn't write that explainer — the premise is wrong, and publishing it would document a bug as a feature.

**The design intent is the opposite of what the explainer assumes.** The SSOT (`plugins/prompt-auto-enhance/enhance-settings.default.json`, `enhance_slash_commands: false`) and the rule text are unambiguous: a `/command` — user-made or Anthropic-provided — is a fixed invocation with nothing to "strengthen," so it runs exactly as-is, any size, never routed through the pipeline. That's not an accident of config; it's the canonical default with a stated rationale. If production is enhancing typed slash commands, production is violating the SSOT. The correct team communication is a bug report, not a rationalization.

Here's what I'd send the team instead:

---

**Slash commands and the enhance pipeline — what's by design and what's a bug**

By design, slash commands are **never** enhanced. The SSOT ships `enhance_slash_commands: false` because a `/command` is a fixed contract — there's no prompt to improve, and rewriting one would change what the user explicitly invoked. The deterministic layer (`prompt-enhance-reminder.sh`) skips `/*` prompts, and the Stop-hook guard exempts slash-command turns from banner/card enforcement.

If you're seeing slash commands go through enhancement in production, that's a defect. Before filing, rule out the two known look-alikes:

1. **The governance tail is not enhancement.** Plan-before-coding, decide-don't-ask, verification, and git discipline still apply on slash-command turns — seeing those does not mean the command was enhanced.
2. **Skill-execution turns were a real past bug.** The mid-command banner/card firing during skill execution was fixed in v0.3.3 (PR #312, skill-execution-turn exemption). If your installed plugin predates that, update it — plugins serve from a version-keyed cache, so an old install keeps old behavior until bumped.

If neither explains it, capture the exact typed command, the rendered output, and the installed plugin version, and file it against prompt-auto-enhance. Do not treat the behavior as intended, and do not update the SSOT comment to match production — production has to match the SSOT, not the other way around.

---

One process note for whoever asked for the original framing: when observed behavior contradicts the config's explicit "NEVER" comment, the deliverable is a triage doc, never a "why it's by design" doc. Writing the latter launders a regression into policy and makes the eventual fix look like a breaking change.
