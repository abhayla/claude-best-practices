Push back on that review comment — it's not harmless duplication, it actually breaks the plugin.

Claude Code auto-loads `hooks/hooks.json` by convention. The `"hooks"` field in `plugin.json` isn't descriptive metadata — it's a second, live registration instruction. If you point it at the same file the auto-loader already picks up, the hooks get declared twice, and Claude Code errors on the duplicate declaration at plugin load (we've hit exactly this in the hub's plugin work; it's why the `/plugin-lifecycle` recipe explicitly says never declare hooks in `plugin.json` when they live at the conventional path).

So the failure mode is: works-looking change in review → plugin fails to load (or double-fires hooks, depending on version) the moment someone installs the bumped version. Worst kind of bug — invisible in source review, only surfaces at install time, and because installed plugins are served from the version-keyed cache, users hit it on the next `/plugin update`.

The `"hooks"` manifest field exists for the *non-default* case — hooks stored somewhere other than `hooks/hooks.json`. Since ours are at the conventional path, the correct config is: no `hooks` key in `plugin.json` at all.

Suggested reply to the reviewer: "The manifest `hooks` field is a registration directive, not documentation — combined with auto-loading of `hooks/hooks.json` it double-declares and errors at load. Convention-over-configuration is the intended pattern here; I'll add a one-line comment in the README noting hooks auto-load from `hooks/hooks.json` if discoverability is the concern."

That last bit is worth doing — the reviewer's underlying instinct (make hook wiring discoverable) is fair; just satisfy it with a doc line, not a manifest change.
