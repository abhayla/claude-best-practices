Short version: the system is not behaving this way on purpose. The "we disabled retries" explanation doesn't match what's actually deployed — the config has retries **enabled**, and the log shows the runtime ignoring that config. This is a bug (config not taking effect), not a design decision working as intended.

## The evidence contradicts the "intentional" story

Two facts are in direct conflict with "we disabled retries":

1. **The deployed config enables retries.** `retries.enabled: true`, `max_attempts: 4`, `backoff: exponential`. If someone had made a deliberate decision to turn retries off, this file would say `enabled: false` (or `max_attempts: 1`). It says the opposite. Whatever anyone *intended*, the disable was never actually committed to the config the system runs on.

2. **The log's smoking gun is "attempt 1 of 1".** With `max_attempts: 4`, a failed delivery should read "attempt 1 of 4", then back off and retry up to three more times. Instead the runtime thinks the ceiling is **1** and gives up immediately on the 503. The effective `max_attempts` at runtime is 1, not the 4 that's in the file.

So the config says 4, the runtime behaves as 1. Retries aren't disabled by design — they're **enabled in config and not being applied at runtime.**

## Most likely root causes (in order)

- **Stale/unreloaded config** — the process is still running an older config (or an env/flag override) where retries were off or `max_attempts: 1`, and the deployed `webhooks.yml` never got picked up (no restart/reload, or it's reading a different file/path than the one we're looking at).
- **Config not being read correctly** — the delivery code isn't reading `delivery.retries.max_attempts` (e.g. it looks for a flat `delivery.max_attempts`, or doesn't honor `retries.enabled`), so it silently falls back to a default of 1 attempt. The file is valid but effectively dead config.
- **Less likely: 503 treated as terminal** — but if 503 were simply on a non-retryable list, we'd expect "attempt 1 of 4 — non-retryable, giving up", not "1 of 1". The "1 of 1" points at the attempt ceiling, not the status classification.

## On the duplicate-side-effects concern

That worry is legitimate — retrying a POST that already committed an order *can* double-fire side effects. But the correct fix for that is **idempotency** (idempotency keys / dedup on the receiver), not silently dropping all retries. Dropping retries doesn't prevent duplicates; it just guarantees we permanently lose deliveries on any transient blip. And a 503 is the textbook *retryable* case: the receiver was temporarily unavailable and almost certainly never processed the request, so there's no side effect to duplicate. We're currently getting the worst of both worlds — no retries *and* no idempotency guarantee.

## What I'd do next

1. Confirm the runtime's *effective* config — log or dump what `max_attempts` / `enabled` the delivery worker actually loaded at startup, and confirm which file/env it read. I expect it to say 1, not 4.
2. If it's stale config → redeploy/restart so `webhooks.yml` actually loads, and verify the log flips to "attempt 1 of 4".
3. If it's a read/parse bug → fix the key path so `delivery.retries.*` is honored, add a test that asserts a 503 triggers 4 attempts with exponential backoff.
4. Independent of the above, add an **idempotency key** to deliveries so we can retry safely and put the duplicate-side-effect worry to rest for good.

Net: don't close this as "working as intended." The intended state per the config is 4 attempts with backoff; the system is doing 1 and quitting. Something between the config file and the running process is swallowing the retry setting, and that's what we should chase.
