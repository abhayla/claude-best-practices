Here's what the evidence actually says, and it's a bit more interesting than either "it's broken" or "it's intentional."

## The config and the log contradict each other

The deployed `webhooks.yml` says retries are **on** (`enabled: true`, `max_attempts: 4`). But the log line says:

```
POST /hooks/order-created -> 503 (attempt 1 of 1) ... giving up
```

`attempt 1 of 1` is the smoking gun. The delivery worker is printing its *effective* retry policy, and it believes the max is **1** — not 4. This is not the "503 classified as non-retryable" case (that would log attempt 1 of 4 with a non-retryable reason, or exhaust retries against a persistent 503). The runtime simply never had `max_attempts: 4` in effect.

## So both statements are half-right

- The reporter is right that **retries aren't happening** — a 503 is exactly the transient failure retries exist for, and we gave up after one shot.
- The teammate is probably right that **someone disabled retries deliberately** — but crucially, *not in this file*. If retries were intentionally turned off, it was done via a different mechanism that overrides or bypasses the YAML: an environment variable (`WEBHOOK_RETRIES=off` style), a feature flag, a hardcoded default in the delivery worker, or the service reading a different config file/path than the one we're all looking at.

That leaves us in the worst state: **the YAML is now a lie.** It says `enabled: true, max_attempts: 4`, the system does 1-and-done, and we just spent a debugging round rediscovering that. (One other candidate worth ruling out: the YAML edit landed but the service was never restarted/reloaded, so it's still running an older config. Same symptom, same fix below.)

## What we should do

1. **Find the real switch.** Grep the delivery worker for where the retry count actually comes from (env var, flag, default) and confirm which config source wins. Check deploy timestamps vs. the last config reload while we're at it.
2. **Make one source of truth.** Whatever the decision is — retries on or off — it must live in `webhooks.yml` and nowhere else. Delete the override. A config file that doesn't describe production behavior is worse than no config file.
3. **Log the effective config at startup.** One line — `webhook retries: enabled=false max_attempts=1 (source: ENV override)` — would have made this a 30-second diagnosis instead of a team thread.
4. **Revisit the decision itself.** "We disabled retries to avoid duplicate side-effects" is treating the symptom. If a consumer can't tolerate an occasional duplicate, the fix is **idempotency, not no retries**: send a delivery ID / idempotency key with every webhook (most of us already have one in the payload) and have consumers dedupe on it. Webhooks are at-least-once by nature — even without retries, a timeout after the consumer processed but before we read the response produces a duplicate on the *next* event anyway. Disabling retries doesn't buy exactly-once; it just converts every transient 503 into silent data loss. With idempotency keys in place, we can safely turn `max_attempts: 4` + exponential backoff back on, which is what the config already promises.

**TL;DR:** The system is behaving as *someone* configured it, but not as *this file* configures it — retries are being suppressed by an override outside `webhooks.yml`. Fix the config drift first, then replace "no retries" with "retries + idempotency keys," which addresses the duplicate-side-effect concern without dropping deliveries on every blip.
