No — that command gives you an empty branch, not your refactor.

**What `git checkout -b refactor/shared-landing origin/main` actually does:** the third argument is the *start point*. So it creates `refactor/shared-landing` pointing at `origin/main` and checks it out — deliberately ignoring your current HEAD. Your 3 refactor commits live on `auto/work-0710`, which is 3 ahead of `origin/main`, so the new branch would contain **zero** of them. `git log origin/main..HEAD` on the new branch would be empty, and a PR from it would be empty. (Nothing is lost — the commits still sit on `auto/work-0710` — but the new branch isn't what you want.)

**What you actually want:** a new name pointing at your current HEAD, which already *is* "the 3 refactor commits on top of main." Just omit the start point:

```
git checkout -b refactor/shared-landing
```

With no start-point argument, `-b` branches from current HEAD. `refactor/shared-landing` will point at the same commit as `auto/work-0710`, carrying all 3 commits, cleanly ahead of `origin/main`. Push it and open the PR from there:

```
git push -u origin refactor/shared-landing
```

**Cleanup (optional):** you now have two names for the same commits. Once you've confirmed the new branch is in place (and especially after the PR merges), drop the old one:

```
git branch -d auto/work-0710
```

`-d` is the safe delete — it only succeeds if those commits are reachable from your current HEAD (they are, since it's the same commit), so it won't let you orphan anything.

One caveat worth a glance: this bases your PR on whatever `origin/main` you last fetched. Since `git log origin/main..HEAD` shows a clean 3-commit lead with no divergence, you're fine — but if `origin/main` has moved on the remote since your last fetch, do a `git fetch` first and rebase if you want the PR to sit on top of the latest main.
