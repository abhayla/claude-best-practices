Hold off — this isn't a behavior-preserving refactor. It silently changes the page numbering convention from 1-based to 0-based.

- Old: `page=1` → `start=0` → first page. Pages are **1-indexed**.
- New: `page=1` → `items[per_page : 2*per_page]` → that's the **second** page. New code is **0-indexed**.

So for the same call, every caller shifts by one page:

| page | old (1-based) | new (0-based) |
|------|---------------|---------------|
| 0 | `items[-per_page:0]` → `[]` | items 0..per_page (first page) |
| 1 | items 0..per_page (first page) | items per_page..2·per_page |
| 2 | items per_page..2·per_page | items 2·per_page..3·per_page |

Reason not to ship: unless you've migrated **every** caller (and any API/URL params, stored links, tests) to 0-based pages in the same change, this hands back the wrong page. Classic off-by-one that passes review because both versions "look clean" — the bug is in the contract, not the code.

Options:
1. Keep it 1-based (behavior-preserving) — just tidy the original:
   ```python
   def page_slice(items, page, per_page):
       start = (page - 1) * per_page
       return items[start:start + per_page]
   ```
   That's already about as simple as it gets; the new version isn't meaningfully simpler, just differently-indexed.
2. If you genuinely want 0-based pages, fine — but then it's a breaking API change, not a "tiny refactor." Ship it with the caller migration + updated tests + a note, not quietly.

One more thing to add regardless: a test pinning `page_slice(range(10), 1, 3)` to a specific expected slice would have caught this instantly. Worth adding so the convention can't silently flip again.

Short answer: don't ship as-is.
