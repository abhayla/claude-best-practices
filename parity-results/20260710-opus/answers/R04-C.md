**Diagnosis: this is not a backfill delay — GA4 is doing exactly what your code tells it to. Every visitor is defaulted to "consent denied" and nothing ever flips it to "granted," so analytics is permanently off for 100% of traffic.**

**Root cause**

1. `gtag('consent', 'default', { analytics_storage: 'denied' })` runs on every page load. That's correct and required for a consent banner.
2. But Consent Mode is a two-part contract: the `default` call sets the pre-choice state, and the banner's accept handler must fire `gtag('consent', 'update', { analytics_storage: 'granted' })` when the user consents. You've confirmed there is **no `update` call anywhere in the codebase**. So even users who click "Accept" on the banner stay denied forever — the banner is UI theater with no wiring to gtag.
3. With `analytics_storage: 'denied'`, GA4 sets no cookies and no persistent `client_id`. In advanced consent mode it sends anonymous cookieless pings, but those don't produce reported *users* unless behavioral modeling is enabled (which requires eligibility + weeks of consented data you don't have — and you have zero consented hits anyway). Net result: ~0 users, exactly matching what you're seeing.

Two secondary things to check while you're in there:

- **The snippet as pasted is also missing the loader and bootstrap.** If it's literally this, there's no `<script async src="https://www.googletagmanager.com/gtag/js?id=G-XXXX">` and no `window.dataLayer = window.dataLayer || []; function gtag(){dataLayer.push(arguments);}` definition — in which case every `gtag(...)` call throws `ReferenceError` and nothing sends at all. Check the browser console. (If those exist elsewhere on the page, ignore this point; the consent-update gap alone fully explains the symptom.)
- The `default` call must execute **before** the gtag.js loader, which your ordering appears to do — keep it that way.

**Why marketing's theory is wrong (say this directly):** GA4 realtime reports within seconds and standard reports finalize within 24–48 hours. There is no three-week "backfill" mechanism, and waiting another week will produce another week of zeros. Worse: **the three weeks of lost data is unrecoverable** — GA4 cannot retroactively ingest it. Every day of waiting adds to the permanent gap.

**Fix**

1. Wire the consent banner's callbacks to gtag:
   ```js
   // on accept
   gtag('consent', 'update', {
     analytics_storage: 'granted',
     ad_storage: 'granted'   // or per-category, matching your banner's choices
   });
   ```
   Most banner libs (Cookiebot, OneTrust, CookieYes, etc.) have a documented Google Consent Mode integration or an `onAccept`/`onConsentChange` hook — use that rather than hand-rolling if available.
2. On **subsequent** page loads for a user who already consented, either re-issue the `update` immediately after the `default` (reading your banner's stored choice), or set the default from the stored choice — otherwise returning visitors are denied again until the banner lib re-fires.
3. Verify before declaring victory: open the site, accept the banner, and check the Network tab for the `google-analytics.com/g/collect` request — the `gcs` parameter should read `G111` (granted) instead of `G100` (denied). Confirm the visit appears in GA4 **Realtime/DebugView** within a minute. That's a five-minute test; no waiting required.
4. Optional follow-ups: enable behavioral modeling (Admin → Data settings → Data collection) so denied users are statistically modeled rather than invisible, and keep server logs as your ground-truth traffic baseline — post-fix, GA4 will still report *fewer* users than the logs, by roughly your consent-decline rate plus ad-blocker usage. That delta is expected and normal, not a bug.

**Bottom line:** decline the "wait a week" plan. Ship the `consent update` wiring today, verify via the `gcs` param + Realtime, and set the expectation that GA4 numbers restart from the fix date — the gap since the banner launched is gone for good.
