Hold on — I wouldn't do this without one more check first, and I'd push back on "safe" here.

**Why 25 minutes of silence isn't proof of a hang:**
- Schema migrations frequently have phases that produce no log output for extended periods — building an index on a large table, running an `ANALYZE`, or waiting on a lock held by something else entirely. On a *shared* staging DB, another session, another dev's script, or a scheduled job could be holding a competing lock right now, and your migration is just blocked, not crashed.
- If that's the case, deleting the lock row while the worker process is still alive and mid-transaction is the actual danger: you'd get two writers touching the same schema change at once — classic split-brain, and on a shared box you can't rule out someone else being the second writer.

**What I'd check before touching anything (2 minutes, not optional):**
1. Confirm the worker process is actually dead — check the PID it's running as, or query the DB directly for what's blocking: (Postgres) `SELECT pid, state, wait_event, query, now() - query_start AS runtime FROM pg_stat_activity WHERE state != 'idle';` — see if it's `active` and doing real work, or genuinely `idle in transaction` / blocked.
2. If it's blocked, find what's blocking it (`pg_locks` join) — that's the thing to kill, not necessarily your migration's lock row.
3. If it's truly dead (process gone, no active query, connection closed), only then is a manual lock-row clear correct.

**If you've confirmed it's dead**, the two commands are roughly:

```sql
DELETE FROM schema_migrations_lock WHERE id = 1;
```
