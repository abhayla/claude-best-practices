## STEP 3 — Output Evaluation

**3.1 Necessity baseline (3 prompts, without vs with skill):** material improvement in all 3.
Without the skill, a careful engineer might still catch the gap, but a rushed one accepts
"tests pass" / "200 OK" / "exit 0" as done. With the skill, STEP 2's channel table names the
exact silent-failure mode each time (plugin-cache trap, CI-green-≠-probe, notification
accepted-≠-delivered) and STEP 5 forces an honest `SOURCE-ONLY-VERIFIED` label with a concrete
follow-up instead of a plausible-sounding "ship it." Skill clearly adds value — not marginal.

**3.2/3.3 Scenarios: 5/5 (3 happy-path + 2 edge-case), each in clean context**
All 5 produced correctly-formed `EFFECT VERIFICATION` blocks with defensible verdicts. Edge case 1
(a pure internal, same-file refactor with no external consumer) surfaced a genuine skill gap:
STEP 2's channel table has no row for an in-process/same-file consumer, and STEP 3's blanket
constraint ("unit tests... are SOURCE checks, not destination probes") is in tension with that
case, since for a same-process caller the unit test IS the consumer's read path. The evaluator
had to make an interpretive judgment call rather than follow a written instruction. Edge case 2
(re-probe after an unrelated edit to an already-verified surface) was handled cleanly — the
explicit MUST DO line ("re-probe after any subsequent edit") gave an unambiguous answer.

**Recommended fixes** (mapped to the STEP 2 routing/channel table and adjacent procedure steps —
report only, SKILL.md not edited per task scope):

1. **STEP 2 table — add an "internal/same-process consumer" row.** Same-file/same-module
   refactors with no external consumer currently fall through the table's cracks and collide with
   STEP 3's blanket "unit tests are SOURCE checks" constraint. A row clarifying that for a
   same-process caller, the existing test suite/call-site trace IS the destination probe would
   remove the interpretive judgment call surfaced in Edge Case 1.
2. **STEP 2 table (or a new row) — add multi-consumer / oversized-input guidance.** State whether
   STEP 1/STEP 5 repeat per consumer (one `EFFECT VERIFICATION` block per consumer) or require an
   aggregate verdict, so a 6-consumer deployment isn't left to agent improvisation (Stress #4).
3. **STEP 1 — add a clarifying-question fallback for zero-context input.** Before the "redesign
   it" fallback, add: if the change itself is unnamed/unclear, ask one clarifying question rather
   than declaring unverifiable outright (Stress #5).
4. **STEP 3 constraint — add a "no test/scratch environment exists" branch.** Currently only
   covers "consumer is a future session/another machine → nearest real proxy." Add explicit
   guidance for the case where the probe is buildable in principle but blocked right now (build a
   minimal scratch env vs. accept a weaker proxy vs. defer with a named follow-up) (Stress #6).
5. **MUST DO — add a time-based re-probe trigger alongside the edit-based one.** "Always re-probe
   after any subsequent edit to the same surface" should gain a sibling clause for elapsed
   time/environment drift with no corresponding edit (cache purge, token rotation, redeploy since
   last verification) (Stress #9).
6. **Cross-reference `plugin-lifecycle` in the description (or vice versa).** Add one clause
   noting that `plugin-lifecycle`'s own "verify installed" step already applies this skill's
   principle to the plugin-fix domain, so the two skills' overlapping activation on plugin-fix
   queries (Q3, Q7) reads as intentional layering rather than duplication.

None of these are blocking — the skill triggers reliably, adds clear value over no-skill baseline,
and never produces a dangerous/incorrect verdict. They are scope-completeness gaps a FIX pass
should close.
